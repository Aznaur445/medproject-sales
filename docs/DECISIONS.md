# Технические решения

## Стек
- **Python 3.12, FastAPI, SQLAlchemy 2, Alembic, PostgreSQL 17.** Стандарт, который хорошо поддерживается.
- **Celery + Redis + Celery beat**, а не ARQ/APScheduler. Нужны встроенные повторы с задержкой, лимиты скорости для писем, `acks_late` (задача, прерванная падением, выполняется заново) и зрелые инструменты. Все задачи пишутся идемпотентными.
- **Серверный рендер (Jinja2 + HTMX)**, а не React/Next.js. Один язык, один образ, нет сборки фронтенда, быстро работает с телефона. HTMX подключён локально (`app/web/static`), без внешних CDN.
- **Сессия:** подписанная cookie (`HttpOnly`, `SameSite=Lax`, `Secure` в prod) с номером версии сессии. Кнопка «Выйти везде» и смена пароля увеличивают версию, и все старые сессии перестают работать.
- **2FA TOTP обязательна.** Без кода вход невозможен. При первом входе показывается QR-код. Каждый код можно использовать только один раз.
- **Защита от подбора:** 5 неудачных попыток → блокировка на 15 минут по IP и по логину. Для несуществующих логинов время ответа такое же, как для существующих.
- **CSRF-токен** во всех формах и запросах HTMX.
- **Логи** в JSON, e-mail и телефоны маскируются, пароли и токены вырезаются (`app/core/logging.py`).

## ИИ-провайдер: DeepSeek, запасной вариант YandexGPT
- Весь ИИ-слой пишется через общий интерфейс `LLMProvider` (этап 4). Провайдер выбирается в `.env` (`LLM_PROVIDER`).
- **152-ФЗ.** Серверы DeepSeek находятся в Китае. Передача туда персональных данных считается трансграничной и требует уведомления Роскомнадзора. Поэтому сервис **не передаёт в ИИ персональные данные**: перед отправкой ФИО, e-mail и телефоны заменяются метками (`[EMAIL_1]`, `[PHONE_1]`, `[PERSON_1]`), а после ответа подставляются обратно. Уходят только данные об объекте и закупке.
- **Коммерческая тайна.** Расценки, себестоимость и маржа в ИИ не передаются никогда. Цену считает детерминированный калькулятор, а ИИ только пишет текст.
- Если DeepSeek окажется недоступен (оплата, качество русского текста, блокировки), переключаемся на YandexGPT одной строкой в `.env`.

## Хранение данных
- Сервер и база в РФ (Timeweb Cloud): требование локализации ПДн, 152-ФЗ ст. 18 ч. 5.
- Бэкапы каждый день в 03:30 МСК: локально и в S3 Timeweb Cloud, хранятся 14 дней. Перед восстановлением проверяются контрольные суммы.

## Мониторинг
- `/health` проверяет БД, Redis и «пульс» обработчика, планировщика и бота. При проблемах отвечает HTTP 503.
- Внутренний сторож (раз в 5 минут) пишет владельцу в Telegram при сбое компонента.
- Uptime Kuma проверяет `/health` извне и сообщает о сбое, даже если упал сам обработчик задач.
- Docker сам перезапускает упавший контейнер (`restart: unless-stopped`). Перезапуск по healthcheck в обычном Docker не работает, поэтому зависание контейнера ловит Uptime Kuma и присылает алерт.

## Обновления
- Автообновлений нет. Обновление только командой `./scripts/update.sh`: бэкап → `git pull` → пересборка.

## Отправка писем (этап 2)
- **Согласование привязано к содержимому.** При «Согласовано» сохраняется хеш адресата, отправителя, темы, текста и вложений (с SHA-256 файла). Перед отправкой хеш сверяется заново: любое изменение, даже прямо в базе, блокирует отправку.
- **Не больше одной отправки.** Статус «отправляется» фиксируется в базе до обращения к SMTP. Если процесс упал во время отправки, письмо не отправляется повторно автоматически, а владелец получает просьбу проверить «Отправленные». Ошибка подключения или авторизации безопасна, такое письмо ставится в очередь повторно.
- **Цена в КП — только итог.** `ProposalContent` (данные для шаблона) не содержит полей себестоимости и маржи. Тест проверяет, что их нет в готовом DOCX.
- **Расценки версионируются**: каждое сохранение создаёт новую версию, а расчёт ссылается на версию, по которой он сделан.
- **КП**: шаблон `app/docx_templates/default.docx` (docxtpl), собирается скриптом `scripts/build_proposal_template.py`. Его можно открыть в Word и поменять оформление, если не трогать теги `{{ }}` и `{% %}`. PDF делает LibreOffice headless в изолированном профиле.
